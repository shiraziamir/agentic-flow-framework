Agentic Flow Framework

Version 1.1.1 · 2026-09-09
Repository-first, tool-agnostic engineering with coding agents.

Durable project memory; disposable, high-quality working context.

1. Purpose

The goal is not token reduction by itself. The framework optimizes for signal-to-context ratio, bounded authority, reliable verification, and restart-safe state. Common failures come from giant permanent instructions, whole-repository scans, stale chat memory, silent scope expansion, and evidence that exists only in conversation.

REQUEST → TASK CONTRACT → REVIEW/FREEZE → APPLY AUTHORIZATION
        → BOUNDED EXECUTION → VERIFICATION/RECEIPTS
        → INDEPENDENT REVIEW → CLOSURE → DURABLE CHECKPOINT → RESET

2. Core rules

  1. Durable repository state beats conversation memory.
  2. One rule, one authoritative home.
  3. Keep always-on instructions short; load procedures as skills.
  4. Write Definition of Done before implementation.
  5. Drafting is not execution authority.
  6. The executor is not automatically the final judge.
  7. Execution may retry; scope/strategy may not silently mutate.
  8. STOP/BLOCKED is a valid outcome.
  9. Verification must produce risk-proportional receipts.
  10. Reset at durable semantic boundaries, not arbitrary token counts.

3. Instruction architecture

  ↓
AGENTS.md — short map + invariants
  ↓
Task contract
  ↓
On-demand SKILL.md
  ↓
Vendor adapters — CLAUDE.md / GEMINI.md / hooks / config

OpenAI's Harness Engineering report documents why one giant AGENTS.md failed: context is scarce, monolithic guidance becomes stale, and the agent loses useful task/code context. Their working pattern is a short root file acting as a map into repository documentation.

4. Task and skills

A material task should state goal/symptom, hypotheses, scope/non-scope, baseline, uncertainties, Definition of Done, evidence, stop conditions and escalation conditions. For important work, use draft → review/freeze → apply. If the contract proves wrong during execution, stop and amend rather than silently rewriting it.

Skills should declare purpose, activation/non-activation conditions, input/output contracts, mutation authority, dependencies, evidence and fail-closed behavior. A useful starting default is 0–3 load-bearing skills per task.

5. Context engineering

Anthropic describes context as working memory and warns that accuracy/recall degrade as context grows. Everything in the request—including system instructions, messages, tool results, documents and tool definitions—competes for the window.

CORE_CONTEXT    = stable policy + task contract + module map
WORKING_SET     = files/modules allowed to change
REFERENCE_SET   = interfaces/contracts needed for the task
EXCLUDED_SET    = unrelated modules, generated output, dependency trees, huge logs
Prompt cache is not compression. Anthropic states that input, cache-read and cache-creation tokens all count toward the context window; cached prefixes still occupy context.

6. Large modular frontend repositories

Determine affected scope mechanically instead of asking an LLM to read the monorepo. Nx affected uses Git plus its project graph to find the minimum affected project set. TypeScript Project References split a program into smaller projects, improve builds and enforce logical separation.

affected graph
  ↓
module context contract
  ↓
cheap read-only discovery child
  ↓
standard executor on bounded module
  ↓
module-local tests/typecheck
  ↓
expand verification only when dependencies require it
module: checkout
edit_modules: [checkout]
reference_modules: [cart, identity]
public_contracts: [packages/contracts/payment.ts]
exclude: [node_modules/**, dist/**, coverage/**]
local_checks: [npm run test:checkout, npm run typecheck:checkout]
escalate_if: [public_contract_changes, tests_fail_outside_working_set]

Child agents are context firebreaks for discovery, inventory, log reduction and repetitive scans. Return a bounded packet—conclusion, files read, affected modules, evidence, failing checks, unresolved items and next step—not the full transcript. Parallelism protects parent context but may increase total spend when agents duplicate reads.

8. Yara skill telemetry audit

The supplied report shows 14 rows, but Yara documentation defines the canonical skill ID as the basename without .md. Historical telemetry contains both forms and effectiveness_report() groups the raw string. After normalization the sample has 12 canonical skill IDs.

yara_01_live_verify_against_real_stack → triggered 2, applied 1
yara_eval_02_evaluating_a_test        → triggered 3, applied 3

Strongest positive observed-association signals in the supplied sample:

model-routing-and-delegation : 3
diagnose-before-fix          : 2
yara_06_fix_the_fix          : 2
craft-and-apply-task          : 1

These do not prove causality. Also, --last 100 selects up to 100 distinct task IDs present in the local event log, not necessarily the last 100 project tasks. The raw event log is gitignored/local, so GitHub alone cannot independently recompute it.

def canonical_skill_id(value: str) -> str:
    return value[:-3] if value.endswith('.md') else value

Keep rare skills lazy/cold until enough data exists; do not delete them merely because the sample is small. For causal skill evaluation, use a frozen fixture with the skill enabled vs neutralized.

10. Starter policy

context_policy:
  root_instruction_target_lines: 120
  default_edit_modules: 1
  default_reference_modules: 2
  raw_log_to_model: false
  semantic_reset_after_closed_task: true
routing:
  deterministic_first: true
  cheap_readonly_for: [discovery, inventory, log_summarization, classification]
  standard_executor_for: [localized_feature_work, module_scoped_refactor, tests]
  judgment_tier_for: [cross_module_contract_change, architecture, security, ambiguous_root_cause, high_risk_closure]
escalation:
  execution_retry_limit_before_judgment: 2
  expand_scope_only_with_evidence: true
  transfer_raw_conversation: false
verification:
  use_affected_graph_when_available: true
  run_local_checks_first: true
  broaden_tests_on_shared_contract_change: true

These values are starting defaults. Tune with real fixtures and measure rework, regressions, escalation rate, verification completeness, latency and cost per accepted task.
