Agentic Flow Framework

Version 1.1 · 2026-09-09
A repository-first, tool-agnostic framework for reliable engineering with coding agents.

Durable project memory; disposable, high-quality working context.

1. What this framework solves

Long agent sessions often fail because of control-plane problems rather than raw model intelligence: oversized permanent instructions, whole-repository scans, stale chat memory, silent scope expansion, evidence that lives only in conversation, and one agent acting as author, executor and judge.

The goal is therefore not simply “use fewer tokens.” The engineering target is a higher signal-to-context ratio, bounded authority, explicit escalation and restart-safe state.

REQUEST
  ↓
TASK CONTRACT
  ↓
REVIEW / FREEZE
  ↓
APPLY AUTHORIZATION
  ↓
BOUNDED EXECUTION
  ↓
VERIFICATION + RECEIPTS
  ↓
INDEPENDENT REVIEW (risk-based)
  ↓
CLOSURE → DURABLE CHECKPOINT → SAFE CONTEXT RESET

2. Core principles

  1. Repository/durable state beats conversation memory.
  2. One rule has one authoritative home; link instead of copying policy.
  3. Keep always-on instructions short; load procedures as on-demand skills.
  4. Write Definition of Done before implementation.
  5. Drafting is not execution authority.
  6. The executor is not automatically the final judge.
  7. A stronger model means more capability, not magical truth or authority.
  8. Execution may retry; strategy and scope may not silently mutate.
  9. STOP/BLOCKED is a valid outcome when prerequisites are missing.
  10. Verification must produce receipts proportional to risk.
  11. Reset context at durable semantic boundaries, not arbitrary token counts.
  12. Heavy exploration belongs in isolated child contexts.
  13. Deterministic rules belong in scripts/hooks/CI where practical.

3. Instruction and authority architecture

POLICY / engineering constitution
        ↓
AGENTS.md — short map + essential invariants
        ↓
Task contract
        ↓
On-demand SKILL.md procedures
        ↓
Vendor adapter — CLAUDE.md / GEMINI.md / hooks / tool config

OpenAI’s Harness Engineering report documents a real failure mode from a giant AGENTS.md: it crowded useful task/code context and became stale. The successful pattern was a concise map into structured repository documentation. The framework follows that pattern.

4. Task contract and skill routing

A task is an executable contract, not a vague prompt. It should name goal/symptom, hypotheses, scope, non-scope, baseline, uncertainties, Definition of Done, allowed mutation surface, required evidence, stop conditions and escalation conditions.

Skills are reusable procedures. Recommended starting default: 0–3 load-bearing skills per task. Each skill should define purpose, triggers, non-triggers, input/output contracts, mutation authority, dependencies, evidence requirements and fail-closed behavior.

Author ≠ judge. For material work, separate draft → review/freeze → apply. If evidence proves the task contract wrong during execution, stop and amend instead of silently rewriting it.

5. Context engineering

Anthropic’s current documentation treats context as working memory and explicitly warns that more context is not automatically better. Prompt history, retrieved documents, tool definitions and tool results all compete for the same window.

CORE_CONTEXT
  stable policy + task contract + module map

WORKING_SET
  files/modules allowed to change

REFERENCE_SET
  interfaces/contracts required to understand the task

EXCLUDED_SET
  unrelated modules, generated output, dependency trees, huge raw logs

A one-million-token window is capacity, not permission to load a monorepo. A fresh session at a durable task boundary is often cleaner than carrying an old history forward.

Prompt caching is not compression. Anthropic documents that cache-read/cache-creation input still counts toward the context window. Use caching for cost and latency, not as a justification for polluted long-lived sessions.

6. Large modular frontend / monorepo pattern

Use a mechanical dependency graph to define the agent working set before asking the model to reason. Nx affected uses Git plus its project graph to calculate the minimum impacted project set. TypeScript Project References are designed to split a large program into smaller projects with explicit boundaries and build order.

mechanical affected graph
        ↓
module context contract
        ↓
cheap read-only discovery agent(s)
        ↓
standard executor for one bounded module
        ↓
module-local tests/typecheck
        ↓
expand verification only when shared contracts require it

Module context contract

module: checkout
edit_modules: [checkout]
reference_modules: [cart, identity]
public_contracts:
  - packages/contracts/payment.ts
exclude:
  - node_modules/**
  - dist/**
  - coverage/**
local_checks:
  - npm run test:checkout
  - npm run typecheck:checkout
escalate_if:
  - public_contract_changes
  - tests_fail_outside_working_set

Use child contexts for file discovery, import/export inventory, log reduction, test-failure classification and repetitive scans. Return only a bounded evidence packet:

CONCLUSION
FILES_READ
AFFECTED_MODULES
EVIDENCE_REFS
FAILING_CHECKS
UNRESOLVED
RECOMMENDED_NEXT_STEP

Parallelism protects the parent context but does not automatically reduce total cost. Multiple agents repeatedly reading the same 50 files can be more expensive than one cheap inventory pass.

7. Model routing

Routing simple bounded work to cheaper models is an officially supported and practical pattern. Route by uncertainty and blast radius, not merely prompt length.

TierUseAuthority
T0 Deterministicdependency graph, grep/AST, lint, typecheck, test selection, formattingscripts/CI
T1 Cheap read-onlydiscovery, inventory, log summarization, repetitive classificationnormally no mutation
T2 Standard executorlocalized feature, module refactor, tests, bounded bug fixscoped edits
T3 Judgmentarchitecture, ambiguous diagnosis, cross-module contracts, security/data, high-risk closuredecision/review; mutation explicit

Claude Code’s built-in Explore agent is a concrete production-oriented example: separate context, read-only tools and Haiku. Anthropic’s cost guidance also recommends cheaper model routing for simple subagent work.

8. Yara skill telemetry audit

Inspection of Yara’s claude branch confirms that the supplied skill report contains a known identifier-fragmentation issue. The canonical ID is a bare basename without .md, while historical events contain both forms. The report implementation groups the raw string, so the two forms render as different skills.

After normalization, the 14 displayed rows in the supplied report collapse to 12 canonical skill IDs. Two fragmented pairs are:

yara_01_live_verify_against_real_stack
  normalized total: triggered 2, applied 1

yara_eval_02_evaluating_a_test
  normalized total: triggered 3, applied 3

The strongest positive observed-association signals in the supplied sample are:

model-routing-and-delegation : 3
diagnose-before-fix          : 2
yara_06_fix_the_fix          : 2
craft-and-apply-task          : 1
These are not causal proofs. Yara’s own telemetry design correctly separates observed behavior/effects from controlled causality.

Also, --last 100 selects the latest up-to-100 distinct task IDs that exist in the skill-event log; it is not automatically equivalent to the last 100 project tasks. The raw _audit/SKILL_EVENTS.jsonl is gitignored/local, so GitHub alone cannot independently recompute the aggregate.

Recommended reporting fix: canonicalize identifiers at read/report time rather than rewriting the append-only historical log, and add instrumentation coverage and eligible-trigger denominators.

def canonical_skill_id(value: str) -> str:
    return value[:-3] if value.endswith('.md') else value

9. Verification and governance

Evidence strength should be explicit:

ClassExample
CLAIM“this should work”
STATIC_RECEIPTfile/line/diff/config
TEST_RECEIPTnamed test + result
LIVE_RECEIPTreal-stack observation
MUTATION_PROOFbreak → fail → restore → pass
INDEPENDENT_REVIEWcold/read-only audit or reproduction

Use minimal governance for low-risk repositories, standard governance for normal engineering, and draft/freeze/apply + independent review + strong evidence for high-assurance/security/production work.

10. Starter policy

context_policy:
  root_instruction_target_lines: 120
  default_edit_modules: 1
  default_reference_modules: 2
  raw_log_to_model: false
  semantic_reset_after_closed_task: true

routing:
  deterministic_first: true
  cheap_readonly_for: [discovery, inventory, log_summarization, classification]
  standard_executor_for: [localized_feature_work, module_scoped_refactor, tests]
  judgment_tier_for: [cross_module_contract_change, architecture, security, ambiguous_root_cause, high_risk_closure]

escalation:
  execution_retry_limit_before_judgment: 2
  expand_scope_only_with_evidence: true
  transfer_raw_conversation: false

verification:
  use_affected_graph_when_available: true
  run_local_checks_first: true
  broaden_tests_on_shared_contract_change: true

The numeric values are starting defaults, not universal laws. Benchmark them on frozen project fixtures and measure rework, regressions, escalation rate, verification completeness, latency and cost per accepted task.
