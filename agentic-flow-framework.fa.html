چارچوب Agentic Flow

نسخه 1.1.1 — ۹ سپتامبر ۲۰۲۶
مهندسی Repository-first و مستقل از ابزار برای Coding Agentها.

حافظه‌ی durable برای پروژه؛ context کاری کوتاه‌عمر، تمیز و باکیفیت برای Agent.

۱. هدف

هدف این framework صرفاً کم کردن token نیست؛ هدف افزایش signal-to-context ratio، محدود کردن authority، verification قابل اثبات و state قابل‌بازیابی است. بسیاری از failureهای Agentic از giant instruction، خواندن کل repo، chat memory قدیمی، scope expansion پنهان و evidence ناپایدار می‌آیند.

REQUEST → TASK CONTRACT → REVIEW/FREEZE → APPLY AUTHORIZATION
        → BOUNDED EXECUTION → VERIFICATION/RECEIPTS
        → INDEPENDENT REVIEW → CLOSURE → DURABLE CHECKPOINT → RESET

۲. اصول اصلی

  1. Durable repository state از conversation memory معتبرتر است.
  2. هر rule فقط یک خانه‌ی authoritative داشته باشد.
  3. Always-on instruction کوتاه باشد؛ procedureها on-demand Skill شوند.
  4. Definition of Done قبل از implementation نوشته شود.
  5. Draft کردن task authority اجرا نیست.
  6. Executor به‌صورت خودکار final judge نیست.
  7. Execution می‌تواند retry شود؛ scope و strategy نباید silently تغییر کنند.
  8. STOP/BLOCKED نتیجه‌ی معتبر است.
  9. Verification باید receipt متناسب با ریسک تولید کند.
  10. Context در semantic boundary durable reset شود، نه صرفاً با عدد token.

۴. Task و Skill

Task مهم باید goal/symptom، hypothesis، scope/non-scope، baseline، uncertainty، Definition of Done، evidence، stop condition و escalation condition را مشخص کند. برای کارهای material، draft → review/freeze → apply را جدا نگه دار. اگر evidence contract را رد کرد، stop و amend کن؛ آن را وسط execution silently بازنویسی نکن.

Skill باید purpose، trigger/non-trigger، input/output contract، mutation authority، dependency، evidence و fail-closed behavior داشته باشد. starting default مناسب: ۰ تا ۳ Skill واقعاً load-bearing برای هر task.

۵. مهندسی Context

Anthropic context را working memory می‌داند و صریحاً می‌گوید با رشد context، accuracy/recall می‌تواند افت کند. System instruction، messageها، tool result، document و tool definition همه از همان window استفاده می‌کنند.

CORE_CONTEXT    = policy پایدار + task contract + module map
WORKING_SET     = فایل/ماژول مجاز برای تغییر
REFERENCE_SET   = interface/contractهای لازم
EXCLUDED_SET    = ماژول بی‌ربط، generated output، dependency tree، log خام بزرگ
Prompt Cache مساوی Compression نیست. Anthropic می‌گوید input، cache-read و cache-creation token همگی در context window حساب می‌شوند؛ cache برای cost/latency است، نه ظرفیت اضافی.

۶. Frontend بزرگ و ماژولار

به‌جای این‌که LLM کل monorepo را بخواند، affected scope را مکانیکی بساز. Nx affected با Git و project graph حداقل projectهای تحت تأثیر را پیدا می‌کند. TypeScript Project References هم برنامه‌ی بزرگ را به projectهای کوچک‌تر با separation و build order واضح تقسیم می‌کند.

affected graph
  ↓
module context contract
  ↓
cheap read-only discovery child
  ↓
standard executor روی module محدود
  ↓
module-local tests/typecheck
  ↓
گسترش verification فقط وقتی dependency لازم کند
module: checkout
edit_modules: [checkout]
reference_modules: [cart, identity]
public_contracts: [packages/contracts/payment.ts]
exclude: [node_modules/**, dist/**, coverage/**]
local_checks: [npm run test:checkout, npm run typecheck:checkout]
escalate_if: [public_contract_changes, tests_fail_outside_working_set]

Child agent برای discovery، inventory، log reduction و scan تکراری مناسب است. به parent فقط conclusion، files read، affected modules، evidence، failing checks، unresolved و next step برگردان؛ نه transcript کامل. Parallelism context parent را حفظ می‌کند ولی اگر Agentها خواندن فایل‌ها را تکرار کنند می‌تواند total cost را بیشتر کند.

۸. Audit Skill Telemetry یارا

گزارشی که فرستادی ۱۴ row نشان می‌دهد، اما documentation یارا canonical skill ID را basename بدون .md تعریف کرده است. telemetry تاریخی هر دو فرم را دارد و effectiveness_report() raw string را group می‌کند. بعد از normalization، sample شما ۱۲ Skill canonical دارد.

yara_01_live_verify_against_real_stack → triggered 2, applied 1
yara_eval_02_evaluating_a_test        → triggered 3, applied 3

قوی‌ترین positive observed-association signalها:

model-routing-and-delegation : 3
diagnose-before-fix          : 2
yara_06_fix_the_fix          : 2
craft-and-apply-task          : 1

این اعداد causality را ثابت نمی‌کنند. همچنین --last 100 حداکثر ۱۰۰ task ID موجود در event log را می‌گیرد، نه الزاماً آخرین ۱۰۰ task واقعی پروژه. Raw event log هم local/gitignored است، پس aggregate آن فقط از GitHub قابل بازشماری نیست.

def canonical_skill_id(value: str) -> str:
    return value[:-3] if value.endswith('.md') else value

Skill کم‌استفاده را فقط با sample کوچک حذف نکن؛ lazy/cold نگه دار. برای causality، fixture یکسان را با Skill enabled و neutralized اجرا کن.

۱۰. Starter Policy

context_policy:
  root_instruction_target_lines: 120
  default_edit_modules: 1
  default_reference_modules: 2
  raw_log_to_model: false
  semantic_reset_after_closed_task: true
routing:
  deterministic_first: true
  cheap_readonly_for: [discovery, inventory, log_summarization, classification]
  standard_executor_for: [localized_feature_work, module_scoped_refactor, tests]
  judgment_tier_for: [cross_module_contract_change, architecture, security, ambiguous_root_cause, high_risk_closure]
escalation:
  execution_retry_limit_before_judgment: 2
  expand_scope_only_with_evidence: true
  transfer_raw_conversation: false
verification:
  use_affected_graph_when_available: true
  run_local_checks_first: true
  broaden_tests_on_shared_contract_change: true

این اعداد starting default هستند؛ با fixture واقعی rework، regression، escalation، verification completeness، latency و cost per accepted task را اندازه بگیر و tune کن.
