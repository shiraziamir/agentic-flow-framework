Frontend

برای ادعای user-visible باید browser/user interaction روی surface واقعی بررسی شود؛ console/network failure، loading/error/empty/permission state و contract کلاینت API در صورت ارتباط بررسی می‌شوند. Screenshot به‌تنهایی receipt برای flow نیست.

Backend

Verification باید در boundary مناسب handler/service/repository انجام شود و validation، authz/tenant/ownership، error path، timeout/retry/idempotency، provider و persistence در صورت ارتباط پوشش داده شوند. پاسخ 200 OK به‌تنهایی receipt برای ذخیره شدن داده نیست.

Shared / Public Contract

Consumerهای affected تا حد ممکن مکانیکی پیدا می‌شوند و فقط producer تست نمی‌شود. Type compatibility لزوماً runtime serialization/protocol compatibility را ثابت نمی‌کند.

Data / Persistence

Representative existing data، migration، write/read، constraint، partial failure، idempotency و rollback/restore boundary در صورت نیاز بررسی می‌شوند. وجود migration file یا موفقیت روی DB خالی برای production-shaped data کافی نیست.

Infra / CI_CD

Target environment/account/cluster، plan/rendered diff، trigger/conditionها، permission، artifact handoff و exact deployed artifact ثبت می‌شوند. CI سبز ممکن است checkهای skipped/neutral داشته باشد؛ گزارش باید مشخص کند چه چیزی واقعاً اجرا شد.

Security / Auth

فقط positive path کافی نیست؛ negative/unauthorized/tenant/ownership path مرتبط و trust boundary واقعی باید بررسی شود. اگر ASVS یا استاندارد دیگری ادعا می‌شود، version و requirement مشخص لازم است.

Reliability / Performance

Baseline و treatment باید قابل مقایسه باشند؛ در صورت اهمیت variance چند مشاهده لازم است و cache، retry، timeout، concurrency، provider و محدوده queryهای log/metric/trace باید روشن باشند.

Blind-Spot Audit

برای HIGH یا MEDIUM پیچیده یک review سرد و read-only دنبال false confidence می‌گردد: ref/environment اشتباه یا stale، consumer/surface جاافتاده، bypass شدن changed path با cache/mock/fallback، proxy ضعیف به جای gate اصلی، gapهای frontend/backend/data/infra/security/reliability و claimهای کلی بزرگ‌تر از universe بررسی‌شده.

Independent Review

Task / DoD / Classification
→ Actual Diff / Source
→ Raw Receipts
→ Independent Falsifying Checks
→ Executor Narrative Last

این ترتیب anchoring روی گزارش Executor را کمتر می‌کند. نتیجه Reviewer یک JUDGMENT است و behavioral receipt گمشده تولید نمی‌کند.

گزارش منعکس‌کننده واقعیت

گزارش باید ref/artifact/environment دقیق، countها، وضعیت‌های PASS/FAIL/PARTIAL/SKIPPED/UNVERIFIED، checkهای مهم اجرا‌نشده، unknownها و residual risk را نشان دهد.

بهتر است بنویسیم:

128/128 required tests passed at commit abc123.
Browser flows A/B passed in testenv X.
Production deployment was not checked.

نه:

Everything is good. No regressions.

کلمات کلی مثل all/none/no regression/secure/fully tested فقط با universe محدود و روش exhaustive مجازند.

Lint مکانیکی

python3 scripts/verification_lint.py <task/evidence/report files>

این ابزار contradictionهای مکانیکی مثل VERIFIED بدون evidence، receipt ضعیف‌تر از minimum، ref قدیمی یا DoD PASS بدون receipt را می‌گیرد؛ اما جای semantic verification و review مستقل را نمی‌گیرد.

Context و History
