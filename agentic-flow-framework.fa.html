اصل مرکزی

حافظه‌ی پروژه پایدار باشد؛ context کاری Agent باکیفیت ولی قابل دورریختن باشد.

تسک‌ها، شواهد، تصمیم‌ها، تاریخ معماری و usage باید durable بمانند، اما Agent روزمره فقط working set لازم برای کار جاری را وارد context کند.

Governance متناسب با ریسک

سطحبرای چه کاریفلو
HIGHمعماری، persistence، production/security/trust، داده پایدار، public contract مهمDraft → Supervisor → Freeze → Apply جدا → Execution → Evidence → Independent Closure
MEDIUMاصلاح محدود داخل همان تسکOwner-approved Amendment → Bounded Apply → Tests/Evidence → Independent Closure
EVIDENCE_ONLYاصلاح داکیومنت، evidence یا test-contract بدون runtime authority جدیدAmendment پایدار + hash/ref → update → closure check در صورت اهمیت

Source of truth روشن، هویت/hash پایدار، STOP قبل از scope creep، ممنوعیت self-certification، عدم جذب Task N+1 و ممنوعیت ساختن evidence مشابهِ چیزی که وجود ندارد در همه سطوح حفظ می‌شوند.

بهره‌وری Token و Model

T0 deterministic/mechanical
T1 cheap read-only discovery/partition
T2 standard bounded execution
T3 judgment/high-risk review

مدل ارزان‌تر فقط جایی استفاده می‌شود که همان کیفیت acceptance قابل حفظ و قابل بررسی باشد. Skill به نام token-efficiency روی whole-repo scan بی‌دلیل، reread سنگین، خواندن history کامل، log خام بزرگ، استفاده از مدل گران برای کار مکانیکی، subagentهای هم‌پوشان، loopهای شکست‌خورده و عبور از budget هشدار می‌دهد.

اگر provider یا harness آمار usage بدهد، با schemas/USAGE_EVENT.md و scripts/usage_ledger.py ثبت می‌شود. اگر عددی در دسترس نباشد، مقدار unknown می‌ماند و تخمین ساختگی ثبت نمی‌شود. Prompt caching ممکن است هزینه/latency را کم کند، اما به‌عنوان context compression فرض نمی‌شود.

Hot State و Cold History

Hot: تسک/Amendment جاری، checkpoint/index، budget و تصمیم‌های حل‌نشده، ماژول‌ها/داک‌ها/Skillهای مرتبط. Cold: تسک‌های بسته‌شده، evidence، judgmentها، تصمیم‌های معماری، usage ledger، timeline و storyها. Cold history فقط برای provenance، audit، regression، retrospective، storytelling یا درخواست صریح کاربر باز می‌شود.

Supervisor

Supervisor می‌تواند انسان، مدل جدا یا session کاملاً سرد باشد. در حالت دسترسی مستقیم، source/diff/test واقعی را بررسی می‌کند. در حالت بدون دسترسی مستقیم، evidence packet محدود را می‌خواند و ادعای غیرقابل اثبات را UNVERIFIED_FROM_PACKET می‌گذارد. نتیجه‌ی مدل گران به‌صورت decision artifact کوتاه ذخیره می‌شود، نه transcript یا reasoning خصوصی.

Storytelling و Self-Branding

Skill به نام project-storytelling فقط هنگام درخواست فعال می‌شود و از indexهای فشرده شروع می‌کند تا داستان پروژه، تکامل معماری، incidentها، تصمیم‌ها، مزیت‌های مهندسی و محتوای portfolio/self-branding را بازسازی کند. Storyهای تولیدشده context دائمی Agent کدنویسی نیستند.

تازگی داکیومنت

داکیومنت‌های canonical و index باید version و تاریخ update داشته باشند. تغییر مهمِ verifyشده Skill documentation-freshness را فعال می‌کند: اول منبع authoritative اصلاح می‌شود و سپس reader viewها و adapterهای generated همگام می‌شوند.
