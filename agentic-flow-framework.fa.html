اصل مرکزی

حافظه‌ی پروژه پایدار باشد؛ context کاری Agent باکیفیت ولی قابل دورریختن باشد.

تسک‌ها، شواهد، تصمیم‌ها، تاریخ معماری، usage و تاریخ اجرای پروژه durable می‌مانند، اما Agent روزمره فقط working set لازم برای کار جاری را وارد context می‌کند.

Governance متناسب با ریسک

سطحبرای چه کاریفلو
HIGHمعماری، persistence، production/security/trust، داده پایدار، public contract مهمDraft → Supervisor → Freeze → Apply جدا → Execution → Evidence → Independent Closure
MEDIUMاصلاح محدود داخل همان تسکOwner-approved Amendment → Bounded Apply → Tests/Evidence → Independent Closure
EVIDENCE_ONLYاصلاح داکیومنت، evidence یا test-contract بدون runtime authority جدیدAmendment پایدار + hash/ref → update → closure check در صورت اهمیت

Source of truth روشن، هویت/hash پایدار، STOP قبل از scope creep، ممنوعیت self-certification، عدم جذب Task N+1 و ممنوعیت ساختن evidence مشابهِ چیزی که وجود ندارد در همه سطوح حفظ می‌شوند.

بهره‌وری Token و Model

T0 deterministic/mechanical
T1 cheap read-only discovery/partition
T2 standard bounded execution
T3 judgment/high-risk review

مدل ارزان‌تر فقط جایی استفاده می‌شود که همان کیفیت acceptance قابل حفظ و قابل بررسی باشد. Skill به نام token-efficiency روی whole-repo scan بی‌دلیل، reread سنگین، خواندن history کامل، log خام بزرگ، استفاده از مدل گران برای کار مکانیکی، subagentهای هم‌پوشان، loopهای شکست‌خورده و عبور از budget هشدار می‌دهد.

اگر provider یا harness آمار usage بدهد، با schemas/USAGE_EVENT.md و scripts/usage_ledger.py ثبت می‌شود. اگر عددی در دسترس نباشد، مقدار unknown می‌ماند. Prompt caching ممکن است هزینه/latency را کم کند، اما به‌عنوان context compression فرض نمی‌شود.

Hot State و Cold History

Hot: تسک/Amendment جاری، checkpoint/index، budget و تصمیم‌های حل‌نشده، ماژول‌ها/داک‌ها/Skillهای مرتبط. Cold: تسک‌های بسته‌شده، evidence، judgmentها، تصمیم‌های معماری، usage ledger، execution ledger، retrospectiveها، timeline و storyها. Cold history فقط برای provenance، audit، regression، retrospective، storytelling یا درخواست صریح کاربر باز می‌شود.

Supervisor

Supervisor می‌تواند انسان، مدل جدا یا session کاملاً سرد باشد. در حالت دسترسی مستقیم، source/diff/test واقعی را بررسی می‌کند. در حالت بدون دسترسی مستقیم، evidence packet محدود را می‌خواند و ادعای غیرقابل اثبات را UNVERIFIED_FROM_PACKET می‌گذارد. نتیجه‌ی مدل گران به‌صورت decision artifact کوتاه ذخیره می‌شود، نه transcript یا reasoning خصوصی.

Execution Retrospective رسمی

برای campaignها، rescueها و migrationهای طولانی می‌توان فایل سرد .agentic/history/EXECUTION_LEDGER.jsonl را نگه داشت. schema آن schemas/EXECUTION_RETROSPECTIVE_LEDGER.md است. این ledger فقط boundaryهای مهم مثل review، amendment، freeze، apply، STOP، evidence-ready و closure را با counter/refهای کوتاه ثبت می‌کند و raw transcript یا evidence تکراری نگه نمی‌دارد.

Skill سرد project-retrospective در صورت درخواست می‌تواند timeline، تعداد task/amendment/review/STOP، defectهای pre-closure، false-completeهای جلوگیری‌شده، implementation در برابر governance commits، روند تست‌ها، mutation/provider/token accounting در صورت وجود telemetry، findings deferشده، governance overhead و تکامل روش کار را بازسازی کند.

PROVEN FROM GIT / DURABLE ARTIFACTS
RECONSTRUCTED FROM OWNER JOURNAL / RECEIPTS
UNKNOWN / NOT LOGGED RELIABLY

برای بخش‌هایی از تاریخ که logging قابل اتکا نیست، عددسازی ممنوع است و وضعیت unknown باقی می‌ماند.

Storytelling و Self-Branding

project-storytelling از audit reconstruction جداست. این Skill شواهد proven/reconstructed را به narrative معماری، case study، lessons learned و محتوای portfolio/self-branding تبدیل می‌کند. اگر retrospective معتبر وجود داشته باشد، ابتدا همان گزارش bounded را مصرف می‌کند تا مجبور نشود کل archive را دوباره بخواند.

تازگی داکیومنت

داکیومنت‌های canonical، index، retrospective و story باید version و timestamp داشته باشند. تغییر مهمِ verifyشده Skill documentation-freshness را فعال می‌کند: اول منبع authoritative اصلاح می‌شود و سپس reader viewها و adapterهای generated همگام می‌شوند.
