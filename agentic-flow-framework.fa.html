چارچوب Agentic Flow

نسخه 1.1 — ۹ سپتامبر ۲۰۲۶
یک چارچوب مستقل از ابزار برای مهندسی قابل‌اعتماد با Coding Agentها.

حافظه‌ی پایدار برای پروژه؛ context کاری کوتاه‌عمر، تمیز و باکیفیت برای Agent.

۱. مسئله‌ای که این چارچوب حل می‌کند

در کارهای طولانی Agentic، مشکل اصلی همیشه ضعف مدل نیست. بسیاری از شکست‌ها از control plane ضعیف می‌آیند: instructionهای دائمی و بزرگ، خواندن بی‌دلیل کل repository، اتکا به حافظه‌ی chat، بزرگ شدن پنهانی scope، مبهم بودن authority، نگه‌داشتن evidence فقط در گفتگو و این‌که یک Agent هم نویسنده‌ی task باشد، هم اجراکننده و هم قاضی نهایی.

بنابراین هدف فقط «کم کردن token» نیست. هدف مهندسی، افزایش نسبت signal به context، محدود کردن authority، escalation صریح و ساختن state قابل‌بازیابی است.

REQUEST
  ↓
TASK CONTRACT
  ↓
REVIEW / FREEZE
  ↓
APPLY AUTHORIZATION
  ↓
BOUNDED EXECUTION
  ↓
VERIFICATION + RECEIPTS
  ↓
INDEPENDENT REVIEW (بر اساس ریسک)
  ↓
CLOSURE → DURABLE CHECKPOINT → SAFE CONTEXT RESET

۲. اصول اصلی

  1. Repository و durable state از حافظه‌ی conversation معتبرترند.
  2. هر rule فقط یک خانه‌ی authoritative داشته باشد؛ به‌جای کپی، link بده.
  3. instruction دائمی کوتاه باشد؛ procedureها به‌صورت Skill فقط هنگام نیاز load شوند.
  4. Definition of Done قبل از implementation نوشته شود.
  5. Draft کردن task مجوز اجرا نیست.
  6. Executor به‌صورت خودکار قاضی نهایی نیست.
  7. مدل قوی‌تر capability بیشتر دارد، نه authority یا حقیقت جادویی.
  8. Execution می‌تواند retry شود؛ strategy و scope نباید silently تغییر کنند.
  9. STOP/BLOCKED نتیجه‌ی معتبر است وقتی prerequisite وجود ندارد.
  10. Verification باید متناسب با ریسک receipt تولید کند.
  11. Context در semantic boundary پایدار reset شود، نه صرفاً با یک عدد token.
  12. Exploration سنگین باید در child context جدا انجام شود.
  13. Ruleهای deterministic تا جای ممکن در script/hook/CI enforce شوند.

گزارش Harness Engineering اوپن‌اِی‌آی یک تجربه‌ی واقعی را شرح می‌دهد: یک AGENTS.md بسیار بزرگ context مفید task و code را کنار می‌زد و به‌مرور stale می‌شد. راهکار عملی آن‌ها تبدیل فایل root به یک نقشه‌ی کوتاه برای رسیدن به documentation ساختاریافته بود. این framework همان الگو را دنبال می‌کند.

۴. Task Contract و Skill Routing

Task باید contract قابل اجرا باشد، نه یک prompt مبهم. حداقل باید goal/symptom، فرضیه‌ها، scope، non-scope، baseline، uncertainty، Definition of Done، محدوده‌ی mutation، evidence لازم، stop condition و escalation condition را مشخص کند.

Skill یک procedure قابل استفاده‌ی مجدد است. default پیشنهادی برای شروع: ۰ تا ۳ Skill واقعاً load-bearing برای هر task. این عدد قانون جهانی نیست و بعداً باید با داده‌ی واقعی پروژه تنظیم شود.

Author ≠ Judge. برای کارهای مهم، draft → review/freeze → apply را جدا نگه دار. اگر هنگام اجرا evidence نشان داد contract غلط است، task را متوقف و amend کن؛ خودسرانه آن را بازنویسی نکن.

۵. مهندسی Context

مستندات فعلی Anthropic صراحتاً context را working memory می‌دانند و هشدار می‌دهند context بزرگ‌تر الزاماً نتیجه‌ی بهتر نمی‌دهد. تاریخچه‌ی prompt، documentهای بازیابی‌شده، tool definitionها و tool resultها همه برای یک window رقابت می‌کنند.

CORE_CONTEXT
  policy پایدار + task contract + module map

WORKING_SET
  فایل‌ها/ماژول‌هایی که اجازه‌ی edit دارند

REFERENCE_SET
  interface/contractهای لازم برای فهم کار

EXCLUDED_SET
  ماژول‌های بی‌ربط، خروجی generated، dependency tree و log خام بزرگ

یک context window بسیار بزرگ مجوز خواندن monorepo کامل نیست. در بسیاری از taskهای مهندسی، fresh session در یک boundary پایدار از carry کردن history قدیمی بهتر است.

Prompt Cache مساوی Context Compression نیست. Anthropic صریحاً می‌گوید cache-read و cache-creation input همچنان در context window حساب می‌شوند. Cache برای هزینه و latency مفید است، نه برای توجیه session بی‌انتها.

۶. پروژه‌های Frontend بزرگ و ماژولار

در frontend/monorepo بزرگ، working set Agent باید از dependency graph مکانیکی به دست بیاید، نه از این‌که مدل کل repo را بخواند. Nx با affected از Git و project graph برای محاسبه‌ی حداقل projectهای تحت تأثیر استفاده می‌کند. TypeScript Project References هم برای تقسیم برنامه‌ی بزرگ به projectهای کوچک‌تر با boundary و build order مشخص طراحی شده است.

        ↓

        ↓
cheap read-only discovery agent(s)
        ↓
standard executor روی یک module محدود
        ↓
module-local test/typecheck
        ↓
گسترش verification فقط اگر shared contract لازم کند

  - packages/contracts/payment.ts

  - node_modules/**

  - npm run typecheck:checkout

  - tests_fail_outside_working_set

برای file discovery، inventory import/export، خلاصه‌سازی build log، دسته‌بندی test failure و scanهای تکراری از child agent جدا استفاده کن. خروجی به parent محدود باشد:

CONCLUSION

AFFECTED_MODULES
EVIDENCE_REFS
FAILING_CHECKS
UNRESOLVED
RECOMMENDED_NEXT_STEP

Parallelism لزوماً ارزان‌تر نیست. چند Agent که همان ۵۰ فایل را دوباره می‌خوانند می‌توانند از یک inventory pass ارزان هزینه‌ی بیشتری بسازند.

۷. Model Routing

بله، تقسیم کار بین مدل‌های ارزان‌تر و قوی‌تر یک الگوی عملی و مستند است. Routing باید بر اساس uncertainty و blast radius باشد، نه فقط طول prompt.

Tierنوع کارAuthority
T0 Deterministicdependency graph، grep/AST، lint، typecheck، test selection، formatscript/CI
T1 Cheap Read-onlydiscovery، inventory، log summary، classification تکراریمعمولاً بدون mutation
T2 Standard Executorfeature محدود، refactor ماژولی، test، bug fix boundededit محدود به contract
T3 Judgmentarchitecture، diagnosis مبهم، cross-module contract، security/data، closure پرریسکdecision/review؛ mutation فقط صریح

Claude Code

T1 → Haiku: exploration/inventory فقط read-only
T2 → Sonnet: coding و execution معمولی
T3 → Opus: architecture و judgment

Explore agent داخلی Claude Code نمونه‌ی واقعی همین الگوست: context جدا، toolهای read-only و Haiku. راهنمای هزینه‌ی Anthropic هم routing کارهای ساده‌ی subagent به مدل ارزان‌تر را توصیه می‌کند.

OpenAI API custom harness

T1 → GPT-5.6 Luna
T2 → GPT-5.6 Terra
T3 → GPT-5.6 Sol

این mapping برای harness مبتنی بر API است و نباید فرض کرد محصول hosted Codex دقیقاً همان menu یا billing را دارد.

OpenCode

OpenCode model override را برای agent و command پشتیبانی می‌کند و child session جدا دارد؛ بنابراین cheap explorer / standard executor / stronger reviewer را می‌توان مستقیم پیاده کرد.

Same-family routing راحت است ولی تضمین کیفیت نیست. روی fixtureهای frozen، ورودی/tool/acceptance gate یکسان را با tier ارزان و استاندارد اجرا کن و quality، rework، regression، latency و cost را مقایسه کن.

۸. بررسی Skill Telemetry یارا

بررسی branch claude یارا نشان داد خروجی‌ای که فرستادی یک مشکل شناخته‌شده‌ی identifier fragmentation دارد. canonical ID باید basename بدون .md باشد، ولی telemetry تاریخی هر دو فرم را دارد. کد report هم raw string را group می‌کند و در نتیجه آن‌ها را Skillهای جدا نمایش می‌دهد.

بعد از normalization، ۱۴ row دیده‌شده در گزارش شما به ۱۲ Skill canonical تبدیل می‌شوند. دو جفت شکسته:

yara_01_live_verify_against_real_stack
  normalized: triggered 2, applied 1

yara_eval_02_evaluating_a_test
  normalized: triggered 3, applied 3

قوی‌ترین signalهای مثبت در همان sample، فقط در سطح observed association:

model-routing-and-delegation : 3
diagnose-before-fix          : 2
yara_06_fix_the_fix          : 2
craft-and-apply-task          : 1
این اعداد causality را ثابت نمی‌کنند. طراحی telemetry یارا درست عمل کرده که observed behavior/effect را از controlled causal proof جدا کرده است.

همچنین --last 100 یعنی آخرین حداکثر ۱۰۰ task ID موجود در event log، نه الزاماً آخرین ۱۰۰ task واقعی پروژه. فایل خام _audit/SKILL_EVENTS.jsonl local/gitignored است و از GitHub نمی‌شود aggregate را مستقل دوباره محاسبه کرد.

اصلاح پیشنهادی: historical log append-only را دست نزن؛ هنگام read/report ID را canonicalize کن و coverage telemetry و eligible-trigger denominator را هم report کن.

def canonical_skill_id(value: str) -> str:
    return value[:-3] if value.endswith('.md') else value

Skillهای کم‌استفاده را فقط به‌خاطر sample کوچک حذف نکن؛ آن‌ها را cold/lazy نگه دار و برای حذف یا promote کردن از fixture کنترل‌شده استفاده کن.

۱۰. Starter Policy

context_policy:
  root_instruction_target_lines: 120
  default_edit_modules: 1
  default_reference_modules: 2
  raw_log_to_model: false
  semantic_reset_after_closed_task: true

routing:
  deterministic_first: true
  cheap_readonly_for: [discovery, inventory, log_summarization, classification]
  standard_executor_for: [localized_feature_work, module_scoped_refactor, tests]
  judgment_tier_for: [cross_module_contract_change, architecture, security, ambiguous_root_cause, high_risk_closure]

escalation:
  execution_retry_limit_before_judgment: 2
  expand_scope_only_with_evidence: true
  transfer_raw_conversation: false

verification:
  use_affected_graph_when_available: true
  run_local_checks_first: true
  broaden_tests_on_shared_contract_change: true

اعداد بالا starting default هستند، نه قانون. با fixture واقعی rework، regression، escalation، verification completeness، latency و cost per accepted task را اندازه بگیر و policy را tune کن.
